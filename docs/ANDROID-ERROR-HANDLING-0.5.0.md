# FLOUSTREAM Android 0.5.0 — понятные ошибки и диагностика подключения

Связанный план: [MESSENGER-0.5.0-PLAN.md](./MESSENGER-0.5.0-PLAN.md)  
Связанный issue: [#4](https://github.com/sergeybikov1991-create/Dolby404/issues/4)

## Цель

Пользователь не должен видеть технические исключения, HTTP-адреса, SQL/JSON, stack trace или красные необработанные сообщения. Любая ожидаемая ошибка авторизации или сети должна превращаться в короткое, понятное сообщение на русском языке с подходящим действием.

Требование относится ко всему Android-приложению: вход/регистрация, обновление сессии, список чатов, загрузка сообщений, контакты, вложения, звонки и социальный раздел.

## 1. Классификация ошибок

### Сеть и DNS
Сюда относятся отсутствие интернета, UnknownHostException / Unable to resolve host, DNS lookup failure, ConnectException, SocketTimeoutException, TLS/SSL handshake/network transport failures и временная недоступность endpoint.

Показывать:
- Заголовок: **Нет подключения к серверу**
- Текст: **Проверьте интернет-соединение и попробуйте ещё раз.**
- Действие: **Повторить**

Не называть это ошибкой пароля и не очищать сессию только из-за сетевой ошибки. При недоступности сети показывать спокойное состояние/баннер, а не сырой красный текст. Сохранять введённый email и несохранённый текст сообщения.

### Неверные учётные данные
Для ответа Supabase Auth с кодом invalid_credentials и эквивалентного ответа при входе показывать:
- Заголовок: **Не удалось войти**
- Текст: **Неверная почта или пароль. Проверьте данные и попробуйте ещё раз.**

Из соображений безопасности не подтверждать отдельно, существует ли указанный email. Не показывать пользователю сырой ответ API.

### Некорректный email / пустые поля
Проверять до сетевого запроса:
- Пустое поле email: **Введите электронную почту.**
- Неверный формат email: **Проверьте формат электронной почты.**
- Пустой пароль: **Введите пароль.**

Подсвечивать конкретное поле нейтральным способом; не выводить техническую ошибку.

### Другие ответы авторизации
- email_not_confirmed: **Подтвердите электронную почту по ссылке из письма.** Предложить повторную отправку письма, если этот сценарий поддержан.
- too_many_requests / HTTP 429: **Слишком много попыток. Подождите немного и попробуйте снова.**
- Истёкшая/отозванная refresh-сессия: безопасно завершить локальную сессию и показать **Сессия завершена. Войдите снова.** Не делать это при временной сетевой ошибке.
- Слабый пароль при регистрации: показать понятное требование к паролю, если сервер его вернул.

### Сервер и прочие ошибки
- HTTP 5xx: **Сервер временно недоступен. Попробуйте позже.** Действие «Повторить».
- HTTP 403: **Недостаточно прав для этого действия.** Не маскировать под ошибку сети.
- HTTP 404: корректное состояние «не найдено» для конкретного экрана/ресурса.
- HTTP 413 / лимит размера: **Файл слишком большой. Выберите файл меньшего размера.**
- HTTP 429: сообщить о частых запросах и предложить подождать.
- Неизвестная ошибка: **Что-то пошло не так. Попробуйте ещё раз.** Предусмотреть безопасный идентификатор ошибки для поддержки.

## 2. Поведение интерфейса

- Не показывать исключения, URL Supabase, query string, названия внутренних классов, stack traces или сырые тела ответов API.
- Все сетевые вызовы UI должны обрабатываться единым слоем преобразования ошибок в типизированные состояния.
- Экран входа должен различать: проверку полей, неверные учётные данные, отсутствие сети, временную ошибку сервера и необходимость подтверждения email.
- При сетевой ошибке не очищать поля email/пароля до явного действия пользователя; пароль не сохранять в постоянное хранилище и не писать в логи.
- Для загрузки данных показывать ненавязчивое состояние «Нет соединения» с кнопкой «Повторить»; при восстановлении сети разрешать повторную загрузку.
- Для фоновых/повторных запросов использовать ограниченные повторы с задержкой (exponential backoff + jitter); не повторять бесконечно запросы входа с неправильными данными.
- Не блокировать навигацию по локальным экранам, если сервер временно недоступен; явно показывать, какие данные недоступны/устарели.
- Сохранять исходную причину ошибки во внутренних диагностических логах без email, паролей, access/refresh токенов, содержимого сообщений и приватных URL.
- Сообщения должны быть локализуемыми; русский — обязательный язык интерфейса на этом этапе.

## 3. Требования к реализации

- Ввести единый тип результата/ошибки для API-слоя (например, NetworkUnavailable, InvalidCredentials, InvalidEmail, EmptyField, EmailNotConfirmed, RateLimited, SessionExpired, Forbidden, NotFound, ServerUnavailable, PayloadTooLarge, Unknown).
- Отдельно классифицировать DNS/transport ошибки и HTTP ответы. HTTP 400 не всегда означает неверный пароль; учитывать код ошибки Supabase Auth, а не только статус.
- Не превращать все исключения в «ошибка сети»: например, неверный пароль, 403 и 500 должны иметь разные сообщения.
- Проверить обработку ошибок во всех трёх разделах приложения, а не только на экране входа.
- Не менять backend auth policies и не добавлять географические ограничения ради этой задачи.
- Не менять веб-сайт; работа только в Android-приложении.

## 4. Приёмочные тесты

### Вход
1. Включить авиарежим / отключить Wi-Fi и мобильные данные, открыть экран входа и отправить форму: отображается понятное сообщение о подключении, приложение не падает, сырой текст исключения отсутствует.
2. Подменить DNS/использовать тестовый недоступный endpoint: показывается то же понятное состояние подключения; сессия не удаляется.
3. Ввести корректный по формату, но неверный email/пароль: отображается «Неверная почта или пароль», без раскрытия существования email.
4. Ввести email неправильного формата: локальная валидация до запроса.
5. Оставить email или пароль пустым: подсказка у соответствующего поля.
6. Смоделировать email_not_confirmed и too_many_requests: соответствующие сообщения.
7. Смоделировать просроченный refresh token: запрос повторного входа; временный DNS/timeout не должен разлогинивать пользователя.

### Работа приложения
8. При потере сети на экране чатов/контактов/соцсети отображается аккуратное состояние и кнопка повторной загрузки.
9. При восстановлении сети повторная загрузка работает без перезапуска приложения.
10. При ошибке загрузки вложения/медиа/звонка показывается понятное действие, без сырого исключения.
11. В интерфейсе нигде не отображаются Unable to resolve host, No address associated with hostname, HTTP request to, необработанный JSON или stack trace.
12. Проверить Android 10 и актуальную поддерживаемую версию Android, Wi-Fi и мобильную сеть.

## 5. Критерии готовности

- Все указанные сценарии покрыты автоматическими тестами классификатора ошибок и UI-тестами ключевых состояний.
- Проведён ручной тест на реальном устройстве с отключением сети, сменой Wi-Fi/мобильной сети и восстановлением соединения.
- Неверные данные входа не маскируются под сетевую ошибку; DNS/timeout не маскируются под неверный пароль.
- Ни одна техническая ошибка не показывается пользователю в сыром виде.
- Выпуск APK — только в составе общего 0.5.0 после полного тестирования; отдельный APK для этой задачи не выпускать.
