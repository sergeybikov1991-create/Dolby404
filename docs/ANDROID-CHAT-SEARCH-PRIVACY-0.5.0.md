# FLOUSTREAM Android 0.5.0 — удаление сообщений, поиск пользователей и скрытие фото

Связанный план: MESSENGER-0.5.0-PLAN.md  
Связанный issue: #4

Все изменения относятся только к Android-приложению. Веб-сайт не менять. Не выпускать отдельный APK до общего релиза 0.5.0 и полного тестирования.

## 1. Удаление сообщений в переписке

### Действия пользователя
- Добавить действие «Удалить» в контекстное меню сообщения (например, долгое нажатие).
- Предусмотреть два разных варианта:
  - **Удалить у меня** — сообщение скрывается только в представлении текущего пользователя; у собеседника оно остаётся.
  - **Удалить у всех** — сообщение удаляется/заменяется tombstone для всех участников диалога; разрешено только автору сообщения и только если это допускает серверная политика.
- Перед удалением у всех показывать подтверждение.
- Для группового диалога (если поддерживается) удалять у всех может только автор сообщения либо роль с явно заданным правом модерации.
- Не показывать действие удаления для чужого сообщения, если у текущего пользователя нет соответствующего права.
- После удаления интерфейс обновляется сразу; результат синхронизируется с другим устройством/участником через Realtime или последующее обновление.
- Для удалённого у всех сообщения показывать нейтральную запись «Сообщение удалено», не оставлять текст или превью вложения.
- Удаление сообщения с вложением должно также безопасно отзывать доступ к соответствующему объекту Storage; не удалять общий объект, пока он используется другим сообщением/ссылкой.
- Сохранять целостность истории и связей reply/reaction/read receipt; не допускать появления удалённого содержимого из кэша или повторной синхронизации.
- Если удаление не удалось из-за сети, не показывать ложный успех: вернуть прежнее состояние или явно отметить ожидание синхронизации и дать повторить.

### Backend и безопасность
- Проверить текущую схему direct_messages и существующие RLS-политики до миграции.
- Реализовать серверно проверяемые права удаления. Нельзя полагаться только на скрытие кнопки в Android.
- Предпочтительно использовать soft-delete/tombstone с минимальными метаданными (кто/когда/тип удаления), не сохраняя удалённый текст в доступном клиентам поле.
- Для «удалить у меня» нужна пользовательская модель скрытия/удаления для конкретного участника, чтобы не менять видимость сообщения другим участникам.
- Для «удалить у всех» авторизация должна проверять автора сообщения и принадлежность к диалогу; неучастник не может удалять сообщения.
- Storage-политики должны исключать дальнейшее скачивание вложения после удаления у всех; физическую очистку делать безопасно и с учётом ссылок.
- Все новые SQL-миграции добавить в supabase/migrations и задокументировать.

### Приёмочные тесты удаления
1. Пользователь A удаляет своё сообщение «у меня»: оно исчезает у A, но остаётся у B.
2. Пользователь A удаляет своё сообщение «у всех»: у A и B появляется нейтральная отметка удаления, содержимое недоступно.
3. Пользователь A не может удалить чужое сообщение у всех.
4. Пользователь B не может удалить сообщение A у всех, если у него нет специального права.
5. Удаление текста, изображения, видео, голосового и файла работает корректно.
6. После перезапуска, повторного входа и синхронизации с другим устройством удалённое содержимое не возвращается.
7. При отключении сети приложение честно показывает, что операция не завершена/ожидает синхронизации; не сообщает об успехе преждевременно.
8. Негативные тесты RLS/Storage подтверждают, что посторонний пользователь не может читать или удалять сообщения и вложения.

## 2. Поиск пользователей

### Интерфейс и поведение
- Добавить доступный из раздела «Контакты» поиск пользователей; также предусмотреть быстрый переход к поиску из главного интерфейса, не перегружая навигацию.
- Поле поиска с подсказкой: **«Имя или @username»**.
- Искать по публичному отображаемому имени и уникальному username/handle, если он существует в текущей модели профиля.
- Не использовать email, телефон или внутренний UUID как публичный поисковый идентификатор и не показывать их в результатах.
- Реализовать поиск по мере ввода с debounce, отменой предыдущего запроса, пагинацией и состояниями: загрузка, результаты, ничего не найдено, нет сети, ошибка.
- Результат показывает только публичные данные профиля, разрешённые настройками приватности: аватар, отображаемое имя, username и публичную информацию.
- Нажатие на результат открывает профиль; доступные действия (например, написать сообщение) определяются настройками приватности и существующими правилами продукта.
- Не раскрывать секретный/приватный фотоальбом и сам факт его существования в карточке результата, профиле, поисковых индексах или рекомендациях.
- Уважать блокировки, ограничения видимости профиля и пользовательские настройки обнаружения. Заблокированные пользователи не должны получать обходной доступ через поиск.
- Не показывать внутренние технические идентификаторы, email, телефон, закрытые поля профиля или приватный контент.
- Если username в текущей схеме отсутствует, сначала изучить профильную модель и предложить совместимый вариант; не добавлять обязательное поле без миграционного плана и проверки существующих аккаунтов.

### Backend и безопасность
- Поиск должен выполняться через Supabase с ограниченным набором возвращаемых полей и серверными/RLS правилами видимости.
- Не скачивать полный список пользователей на устройство для локальной фильтрации.
- Защититься от массового перебора и scraping: пагинация, разумные лимиты частоты, ограничение размера запроса.
- Не раскрывать существование скрытых/заблокированных аккаунтов в обход правил приватности.
- Проверить индексы по нормализованным публичным полям; избегать полного сканирования таблицы профилей.

### Приёмочные тесты поиска
1. Найти второй тестовый аккаунт по отображаемому имени.
2. Найти его по username/handle (если поле поддержано).
3. Частичный ввод, регистр и пробелы обрабатываются предсказуемо.
4. Несуществующий пользователь даёт спокойное состояние «Ничего не найдено».
5. Email, телефон, UUID и закрытые поля не раскрываются и не используются как публичный поиск.
6. Заблокированные и скрытые профили не обходят правила приватности.
7. Результаты постранично загружаются; быстрый набор не вызывает гонок устаревших ответов.
8. Секретный фотоальбом и факт его наличия нигде не появляются в результатах.

## 3. Скрытие фото в полноэкранном просмотре чата

### UX
- При открытии фотографии из переписки в полноэкранном просмотрщике добавить действие **«Скрыть фото»**.
- После нажатия фотография немедленно закрывается визуальной заглушкой/нейтральным экраном с действием **«Показать фото»**; повторное нажатие возвращает изображение.
- Скрытие действует только в текущем просмотре на текущем устройстве и не удаляет фото из переписки, не меняет доступ собеседника и не меняет серверные данные.
- При закрытии полноэкранного просмотрщика и повторном открытии фото отображается обычным образом; постоянную локальную настройку в этом релизе не добавлять без согласования.
- Состояние скрытия должно быть очевидным и обратимым; не путать его с удалением сообщения или приватным альбомом.
- Не показывать само изображение в миниатюре/анимации перехода, пока оно скрыто.
- Проверить поведение системных скриншотов/recents preview: не допускать случайного отображения скрытого изображения в превью приложения, если это возможно в рамках безопасного поведения Android.

### Приёмочные тесты фото
1. Открыть изображение из чата на весь экран — действие «Скрыть фото» доступно.
2. Нажать «Скрыть фото» — содержимое заменяется заглушкой, исходное фото не видно.
3. Нажать «Показать фото» — изображение возвращается.
4. Закрыть просмотрщик и открыть фото снова — обычное отображение; скрытие не удалило сообщение и файл.
5. Проверить портретную/альбомную ориентацию, разные размеры изображений и переходы между фото.
6. Убедиться, что скрытие не меняет видимость фотографии для собеседника и не затрагивает секретный фотоальбом.

## 4. Общие критерии готовности
- Функции реализованы только в Android-приложении.
- Все права удаления и поиска проверяются на сервере; UI-ограничений недостаточно.
- Новые миграции и RLS/Storage изменения включены в репозиторий.
- Пройдены UI, интеграционные и негативные security-тесты на двух тестовых аккаунтах.
- Нет утечки приватного содержимого через поиск, кэш, синхронизацию или удалённые вложения.
- Не выпускать APK отдельно от полного 0.5.0; перед релизом проверить обновление поверх 0.4.0.
